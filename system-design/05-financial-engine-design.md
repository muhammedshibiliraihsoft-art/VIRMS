## Authority and calculation discipline

Post actual monetary events in INR with fixed-precision decimal amounts at two places and ROUND_HALF_UP. Keep percentage intermediates at higher precision; never use binary floating point. A calculated entitlement, loss allocation, payable or reserve designation is not a receipt, payment or Fund credit. Source transactions and linked Fund Ledger movements are immutable, auditable and reconciled; a projection is rebuildable. Each real-world payment has one event identity and one economic effect.

Locking a command means lock its Investor Fund/current position and relevant Vehicle, Sale, recipient adjustment or Settlement in a stable order, then re-evaluate every cap inside the transaction. Section 11 defines the technical protocol. Cash, non-cash recognition, principal, Profit and obligations never silently net across categories.

The claim's equivalent Available-based reconciliation subtracts any combined reserve amount not covered by Gross Fund Ledger Balance; this permits an uncovered Owner return/refund obligation without reporting negative Available Fund or inventing liquidity. ## Exact allocation algorithm

For positive Profit or Loss magnitude, round the Investor percentage share first using ROUND_HALF_UP at two decimals. Owners Pool is the authoritative magnitude minus that rounded Investor share. The applicable Owner recipients and percentages are the immutable Sale snapshot; the configured percentages are nonnegative and total exactly 100%, and a positive pool requires a recipient. For each recipient calculate a high-precision raw share, round provisionally to paise, then calculate pool minus provisional sum. Add a paise at a time to the currently most under-allocated recipient when the residual is positive, or subtract a paise from the currently most over-allocated nonnegative-remaining recipient when negative. Recompute priority after each paise. Stable configured Owner order breaks ties. Stop only at an exact zero residual; no allocation may be negative. Investor share plus Owner shares equals the signed deal magnitude exactly. A zero Owner Pool creates no Owner allocation. Completed historical monetary snapshots remain unchanged; a correction reuses historical percentages/order but calculates a linked corrected position.

## Correction reconciliation

The reusable pattern is: read immutable original and all linked events → compute corrected target from current price/cost and the original snapshot → subtract actual valid effects already confirmed, reversed, paid, recovered, refunded or returned → reconcile one current open position by append-only adjustment → revalidate claim, Fund, payout eligibility and settlement blockers. A correction event identifies chain/version, actor, reason, source, old and new values, timestamp and resulting target. Never reset cumulative actual activity to zero or create a duplicate current payable.

- Sale downward correction can create Buyer Refund Payable and principal-backed reserve. If an actual refund occurs, reverse the latest applied receipt portions first, so collected Profit is reversed before earlier principal. An upward correction adjusts the still-open payable/reserve; an already paid refund remains paid.
- Cost or Sale change can reclassify the original Buyer receipt between Profit and Principal Recovery. Credit only new valid principal, debit a reversed principal allocation unless its refundable portion is held behind a reserve, and debit the principal-backed portion when the actual refund occurs.
- Profit correction uses current corrected entitlement and actual net retained payment. Profit-to-Loss targets zero positive entitlement while separately allocating Loss. No payout recovery is silently offset against Loss coverage.
- Same-side Loss compares corrected Investor share with net recognition, and each corrected Owner requirement with that Owner's actual retained contribution. It records only missing recognition/reversal, obligation or return target. Loss-to-Profit reverses only remaining net recognition, targets Owner return to remaining net contribution, then separately allocates positive Profit.
- Repeated crossovers and post-closure corrections preserve prior closure history while presenting a new linked unresolved current position. Closure cannot be represented as current final resolution until all new blockers are settled.

## Financial command contract

Every command below receives actor/session, relevant UUIDs, an explicit amount when money moves, idempotency key, request fingerprint and reason when correction/audit requires it. It authenticates and checks operation, Tenant, account and object scope per 02/03; validates decimal precision and linked identity; locks the listed current resources in a deterministic order; recomputes the canonical position inside one PostgreSQL transaction; appends source events, linked Fund movement and audit atomically; returns the committed current position. The same key/fingerprint replays the original outcome; a key reused for different input is rejected. Nonpositive, stale, excess and unauthorized input is rejected with no partial posting, clamping or balancing category. Section 11 defines isolation/retry mechanics. These guarantees apply to each row, including when its specific cell is short.

| Command and actor | Input and current-state validation / rejection | Lock domain and immutable events | Derived positions affected / audit |
|---|---|---|---|
| Add Investor Capital — Accountant | Investor, amount > 0, valid account scope; reject duplicate or invalid Investor | Investor Fund; capital source plus Fund credit | Gross/Available/claim; actor and funding source |
| Purchase Vehicle — Accountant | One Investor, Tenant, positive approved cost, Investor Active, sufficient Available Fund; reject cross-Tenant or excess use | Investor Fund then Vehicle; purchase/Vehicle and Fund debit | Used/Available/cost; actor and provenance |

Investor normal Exit Request is a separate lifecycle command requiring own authenticated identity, Terms acceptance and notice; it cannot post finance or bypass the above settlement gates. Back Office configuration and Tenant Merge are not daily financial commands.

## Non-negotiable reconciliation gates

Before an applicable final closure: no outstanding Vehicle principal, Locked Principal, Buyer receivable/refund, required Owner contribution/return, Profit recovery/additional payable or other correction blocker; full principal claim reconciliation; and actual payments of Principal Settlement Payable followed by remaining eligible Investor Profit. Eligible pre-Exit Investor Profit can still be paid under normal deal gates. Reports must show each category separately and never compute a false zero through cross-category netting.
