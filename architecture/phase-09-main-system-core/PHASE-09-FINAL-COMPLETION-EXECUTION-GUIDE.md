## 6. Final mobile and responsive coverage

Use the existing design system and reference UI. Test **320, 390, 768, 1024 and 1440 px** viewport widths. If the browser cannot set a width, record the exact missing evidence as UNVERIFIED instead of claiming a sweep. At each width cover:

- **Shell/navigation:** reachable Dashboard, Vehicles, Jobs, Fund and Accounting; no rail/header/content overlap; menu and logout accessible; page can scroll vertically; no unintended horizontal overflow.
- **Dashboard:** existing card order, color and hierarchy; large values, zero, `Unavailable` and long labels fit; chart axis/legend and zero months remain legible; Recent Activities table can be read without hiding data or actions.
- **Three- and four-KPI rows:** first orange card and remaining light cards retain their approved appearance; text and currency do not clip; stack/grid follows available width; 0 is shown only for successful empty data, while permission/network/blocked states remain distinct.
- **Vehicle and Stock details:** register search/filter, pagination, Details panel, purchase/expense/sale actions and confirmation messages remain usable. Sheets/modals fit short phone height, scroll internally as needed and do not trap buttons beneath fixed UI.
- **Fund, Garage, Sale and Accounting forms:** labels, amounts, date inputs, validation, primary/destructive actions and error messages remain visible. Minimum practical touch area is retained; mobile inputs stay compact. Tables have an intentional overflow or mobile composition, with critical reference/status/amount still findable.
- **State transitions:** loading → ready/empty, 403/409/500/network error, disabled module, successful save → refreshed value, logout → login → saved record still present. No UI success toast after a failed backend mutation.

Capture one representative screenshot or browser observation per changed critical layout at narrow phone and desktop width, plus concise notes for the other widths. Only a reproduced regression justifies a UI change; obtain user approval before a material layout/card change.

Classify each finding **A must fix now, B should fix now, C defer with reason, D informational**. For a confirmed A or required B: reproduce, trace request/data/API/DB/permissions, inspect affected direct consumers and existing tests, make the smallest reversible fix, then run that path's focused regression. For shared auth, tenant, finance, API/schema or migration changes, prepare an impact report and obey the applicable approval gate before editing. Do not weaken a test to make it pass. Do not erase financial history or create calculated money as actual paid cash.

After accepted repairs, perform **one** integrated gate: focused backend suites for changed modules on disposable PostgreSQL, schema/migration checks, relevant React tests/lint/build, authenticated J01–J09 browser journeys, and the responsive sweep. Record exact commands, discovered/run counts, PASS/FAIL, database identity and browser observations. If this gate finds a defect, repair only that path, run its focused check and append a result; avoid rerunning every valid check without a changed dependency.
