## 2. Ownership map

| Fact | Authoritative owner | Garage relationship |
|---|---|---|
| Vehicle identity, registration, current Branch, movement | Vehicle Management | Job references immutable Vehicle UUID; does not copy identity. |
| Job context, work, OPEN/COMPLETED history, agreed customer charge | Garage | Job UUID is stable; each work/charge change retains actor, time, original Branch. |
| Stock Vehicle approved cost and Fund/Running Capital allocation | Existing Vehicle/Investment contracts | Garage work points to the one authoritative Vehicle cost record; no second stock cost posting. |
| External Job approved cost | Garage | Job cost source and bill are separate from actual cash payment. |
| Customer receipt, Cash/Bank movement, Garage Revenue | Accounting | Typed same-Company link connects the actual event to Job/charge. No mirrored Garage cash event. |
| Labour person and manual payment history | Labour boundary | Worker payment is separate from Job cost and cannot silently allocate to a Vehicle. |

## 3. Proposed domain relationships

- `GarageJob`: UUID, Company FK, Vehicle FK, working Branch FK, context (`STOCK` or `EXTERNAL_CUSTOMER`), status (`OPEN`, `COMPLETED`), actor/time and history. Context is snapshotted per Job; it does not change because the Vehicle later changes responsibility or Branch.
- `GarageWorkEntry`: Job FK, description, actor/time, source Branch and retained correction history. Additions/changes require Job OPEN.
- `GarageJobCost`: Job FK, approved description/type/amount, Branch, actor/time, retained correction history. For Stock work, use an explicit link to the one existing `VehicleExpense` or another reviewed Vehicle-owned cost source; the Job total and Vehicle total must reference that same source once. Decide the exact mapping after inspecting the current Vehicle Expense command and payment semantics; no duplicate write is allowed.
- `GarageCustomerCharge`: external Job FK, agreed amount and audited revisions. Charge is a receivable, not a Receipt. The current outstanding amount is derived from the effective charge and linked valid receipts/corrections. A reduction below valid collected amount is rejected.
- External Job service-contact Name and Phone belong on the Job as context fields, not a separate reusable customer identity. **Name is required; Phone is optional** under the 2026-11-17 V2 decision. Phone is not a unique key.
- `LabourPerson` and `LabourPayment`: basic Company/Branch worker, Active/Inactive, manual payment amount/date/optional note/history. The actual Company payment must use an Accounting-owned Cash/Bank event through a reviewed typed source contract; it is never automatically a Vehicle cost.

Every FK relationship must enforce same Company at the command and database integrity boundary where feasible. Deletion of confirmed Job, cost, charge, receipt link or history is denied. Prefer append-only correction/reversal for confirmed financial facts.

## 4. Key workflows and APIs to lock

| User action | Backend flow | Result/UI |
|---|---|---|
| Create/find Job | Authenticate → Company/Branch/module/action check → resolve existing Vehicle → create OPEN Job | Return Job UUID; list/detail reload from backend. |
| Add work/cost | Check original Job Branch, OPEN status and cost owner → save work and approved source link atomically | Show source cost once and source Branch. |
| Complete/reopen | Lock Job → validate allowed transition → append status history | OPEN↔COMPLETED visible with actor/time; no edits while COMPLETED. |
| Set/correct customer charge | External Job only; lock Job and current receipts → reject amount below collected total → retain old/new/reason | Show agreed charge, collected and outstanding separately. |
| Record partial customer receipt | Lock Company/Job/charge and Accounting source in one stable order → authorize Accounting account → validate unique external reference and remaining cap → write one Accounting cash effect and typed Job link atomically | Receipt appears once; balance changes only after commit. Retry returns same result; concurrent overcollection fails. |
| Labour payment | Validate worker, Branch, authorized account and Accounting gate; one actual payment and typed worker-payment link | Worker history shows actual payments; Job cost unchanged unless separately approved. |

Exact route names, request/response fields and error codes are **proposed for the code-level contract**, not already implemented endpoints. Follow the existing `/api/v1` session/CSRF, serializer, Company scope, pagination, error and idempotency conventions. Reject cross-Company IDs before resolving private objects. Distinguish validation, forbidden, not-found and stale/concurrent conflict. External receipt reference is operator supplied and Company-wide unique across Branches as V2 specifies; it is traceability, not record identity.

## 6. Permissions, module gates and history

- Backend checks active Company membership, effective Branch assignment, role/action permission, `garage` module state, Job/Vehicle Company, original Job Branch and object scope on every mutation. Branch selection in UI does not grant authority. Cross-Branch Garage mutation is denied by default; authorized same-Company prior-Branch history may be read.
- Garage must work with Investment OFF for external-customer Jobs. Stock cost/funding operations require their existing owning-module gates. Actual cash writes require Accounting authority and module gate. A Garage role does not inherit Accounting or Investment write power.
- Garage OFF blocks new Jobs, optional expansion and new charge. Authorized history stays readable. Already-open financial obligations are handled only through the authoritative module's approved exception and permissions; do not add a generic Garage bypass.
- Owner remains read-only for ordinary Garage records. Protected automation approval, if later implemented for a specific action, follows the Company-wide mode in V2; this basic slice proposes no automatic money posting.
- Vehicle transfer retains original Job/cost Branch attribution. Existing Vehicle deactivation remains blocked until Garage can authoritatively say no open Job **and** all other Sale/finance/refund/Investor-settlement providers independently report clear.

A Job linked to a Vehicle moved since the Job was opened also needs explicit original-Branch handling; current expense creation takes the Vehicle's current Branch.
- `create_receipt_or_payment` in `apps/accounting/services.py` requires an existing current `INCOME` target and creates an `AccountingApplication`. Accounting `INCOME` affects the bounded Accounting result. Therefore creating a generic Income for the entire Garage charge would prematurely include it in that result while V2 `09` leaves Garage Revenue recognition unresolved. A typed Garage-specific source path must preserve the existing report and satisfy deferred recognition rather than silently reusing this endpoint.
- The existing Vehicle Sale receipt in `apps/vehicles/services.py` uses `execute_domain_mutation`, locks the parent Sale, checks Accounting and domain actions, validates the outstanding amount, and writes the Accounting movement plus typed link inside that transaction. Garage needs an equivalent domain-specific path and a database-enforced Company-wide reference uniqueness rule; a frontend-only check is insufficient.
- `AccountingSourceLink` has an exactly-one-source check and database relationship triggers. Any extension needs an additive migration covering both, alongside event/movement integrity constraints and replay tests. The detailed schema and coordinated lock order remain to be reviewed before code changes.

At the time of this snapshot, the implementation was not `READY_FOR_IMPLEMENTATION`. The current status and verification evidence are recorded below. Full Parts Inventory, payroll, attendance, CRM, customer-credit/refund automation, Investor settlement and broad UI redesign remain outside this basic Phase 6 slice.
